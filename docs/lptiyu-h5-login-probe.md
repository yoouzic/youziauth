# lptiyu H5 登录链实验报告(路线 B)

- 时间:2026-11-13(持续更新)
- 目的:验证乐跑 H5 面(ThinkPHP 独立应用)能否**不经微信**、用学号+密码登录,
  以及登录产物能否换发 v3 `access_token`(跑步提交链唯一认的钥匙)
- 凭据来源:寝室打卡已登记的统一认证凭据(DPAPI 本机解密,用户明确授权)

## ⚠️ 账号锁定事故(2026-11-13)

- **事实**:学号 222025321102104(柚子)在 H5 面累计 3 次密码错误(统一认证密码、
  学号作密码、用户一次候选密码)后,登录应答返回「学号或密码输入有误,**账号已锁定**」。
- **更正**:研究库 lpcore/h5.py 的「实测 5 连错不锁定」记录**不可靠**——
  锁定按**累计错误**计,3 次即触发(至少在 bdlp_h5_fitness_test 面如此)。
  探针已加 60 分钟熔断(`.scratch/lptiyu-h5-probe/lockout.json`),被锁学号
  冷却期内拒绝重试,防止把锁定续期。
- **影响范围(推断,未实测)**:小程序走微信 `loginByCode`,与 H5 密码是两条
  认证路径,H5 锁定**大概率不影响**小程序登录与既有自动化。若小程序也异常,
  立即停止一切尝试并联系体育老师。
- **解锁路径**:等 30-60 分钟自动解锁,或体育老师/管理员重置——
  重置密码恰好同时解决「不知道乐跑专用密码」的问题。
- **纪律更新**:不要用探针暴力试密码;每次实验前确认当前学号没有未过冷却的锁定。

## 🔍 用户观察(2026-11-13):学生登录只有微信/QQ,没有账号密码入口

用户检查后发现小程序等所有入口**只提供微信/QQ 登录,不存在账号密码登录**。
两种解释,证据两边都兼容:

- **可能 A(路线 B 判死)**:学生账号在乐跑平台只有微信/QQ 认证,「学号+密码」
  对学生不开放 → 任何密码都不可能对;多成员凭证库(路线 A,已上线)是唯一方案。
- **可能 B(路线 B 仍可走)**:学生账号由学校批量导入,有默认密码(身份证后六位等),
  只是无人知晓、无人使用。
- **反向旁证**:锁定按学号计数生效,略偏向「账号在密码体系里存在」(可能 B);
  但无法排除无差别计数。

**决定性一步收敛为一句话:问体育老师/管理员「学生在乐跑有没有学号密码?能否查/重置」。**
答无 → 可能 A 坐实,路线 B 关闭;答有 → 熔断冷却后跑一次探针即见分晓。

## 实验结论

1. **协议链全通**:`getToken → verify(PNG 验证码) → login` 全部按研究库观测的
   形态工作;验证码通过后的报错是「学号或密码输入有误」,证明校验顺序为
   验证码 → 学号/密码,与 lpcore/h5.py 的记录一致。
2. **统一认证密码不通用于乐跑 H5**(2/2 样本):
   - 柚子(`222025321102104`)→ 学号或密码输入有误
   - 红兔(`222024329012075`)→ 学号或密码输入有误
   - 学号本身作密码(柚子)→ 同样被拒
   - 锁定阈值:**累计 3 次密码错误即锁**(见上方事故节;研究库旧记录有误)
3. **推论**:免微信添加凭证在原理上可行(H5 面就是一条完整的免微信登录链),
   但前提是拿到**每个人在乐跑系统里的专用密码**(常见初始形态:身份证后六位、
   学号变体,或由体育老师/系统管理员重置)。拿到后用
   `py -3 tools/lptiyu_h5_probe.py --student <学号> --captcha model`
   即可完成「登录 → 看 v3 是否换发 token」的下半场实验。
4. **v3 换发问题仍未回答**(需要一次成功登录才能看到应答里有没有
   `access_token`/`token_data`)。这是路线 B 的最后一块拼图。

## 验证码模型(v3:全自动可用,val 83.4%)

- 现有 IDM 模型对 lptiyu 验证码 **0%**(风格完全不同,直接复用不可行)。
- 为此新建 `lptiyu_captcha.py`:固定阈值 145 二值化 → 水平膨胀熔合断裂笔画 →
  连通域+列宽切分(含宽块预切)→ **槽位归一**(全分辨率 200×60 画布 → 缩到 100×30)。
- 数据:采集 **1440 张**,人工标注 **1431 张**(9 张字形存疑弃用),
  每张 ±8° 旋转变体(×3)= **4278 张**训练图,`tools/captcha/train.py`
  加 `--group-split`(验证集按原图分组,增强变体不跨集防泄漏)重训
  `lptiyu_model.npz`。
- **迭代轨迹(验证集整串)**:
  | 版本 | 原始数据 | 增强 | val 整串 |
  |---|---|---|---|
  | v1 | 313 | 无 | 2-8% |
  | v2 | 633 | 无 | 31.3% |
  | v2.5 | 633 | ±8°×3 | **74.6%**(逐位 88-96%) |
  | **v3** | **1431** | **±8°×3** | **83.4%**(逐位 94.1%) |
- 6 张全新盲测:4/6 整串(67%),答对样本置信 0.92-1.00;按 5 次重试估算
  登录链成功率 ≈ **99.99%** —— 验证码不再是瓶颈,`--captcha model` 全自动可用。
- 数据与权重归档在 `data/captcha/lptiyu/`(19MB:模型 + 标注 + 4278 张训练图 +
  训练报告);管线在 `.scratch/lptiyu-h5-probe/`(采样/标注/预处理/评测一条龙)。
- 用法:`tools/lptiyu_h5_probe.py --captcha model`(默认,失败自动换一张重试);
  `--captcha manual`(验证码 PNG 自动弹出,人工输码)永远可用。

## 远程提取方案(2026-11-13,已交付)

H5 密码路径对学生大概率不存在后,「添加成员」的远程替代方案:

- **提取器**(发给成员的单文件 exe,`tools/lptiyu_credential_export.py`,
  spec: `packaging/lptiyu_extractor.spec`,构建产物
  `.scratch/lptiyu-extractor-dist/lptiyu-credential-export.exe`,18MB):
  成员在**自己的电脑**上双击 → 输入与管理员口头约定的 PIN → 自动装采集 CA
  (Windows 弹窗确认=知情同意)→ 临时指代理 → 唤起小程序 → 进一次跑步首页 →
  桌面生成 PIN 加密的 `lptiyu-credential-*.json` → 立即还原代理。
- **导入端**(两种):CLI `py -3 tools/lptiyu_member_import.py auto <PIN>`
  (自动找桌面/下载最新凭证文件);界面「导入凭证」按钮 → PIN 弹窗 →
  `lptiyu_member_import` 动作自动扫描桌面/下载、解密、按 uid 入档。
- **密封格式**(`lptiyu_credential.py`,9 项测试):AES-128-CBC,
  key=SHA256(PIN)[:16],IV 随机,明文带 LPTCRED1 魔数(错 PIN 秒判)。
- **生命周期事实**:导入的 token 只被"成员自己在任何设备重开小程序"轮换死亡;
  成员若不自用乐跑,一次导入长期有效(与所有者凭证同理)。
  这边能做的是**保活**(探活+不触发轮换),不能铸造新号(铸造权在其微信)。
- **全成员保活巡检**(2026-11-13):后台按续期间隔(≥60 分钟,启动 5 分钟后首巡)
  对每个**非活动**成员的 token 做只读探活,结果进各成员自己的台账;
  死了界面成员栏直接标「凭证已失效」并提示重发提取文件 —— 不用等到切过去
  跑步那天才发现。链路故障不判死(与续期同一语义)。

## 对多成员功能的影响

- 主线不受影响:多成员凭证库(v1.9.16)按小程序采集归档,与路线 B 独立。
- 路线 B 若最终走通(拿到乐跑专用密码并确认 v3 换发),「添加成员」将变成
  纯粹的学号+密码,和寝室打卡完全一致。
