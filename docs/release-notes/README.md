# 更新说明怎么写

客户端「软件更新」页里的「这次更新改了什么」优先显示**发布者手写的中文说明**：
发布时把 `docs/release-notes/v<版本>.md` 作为 `release-notes.md` 资产上传，客户端直接读它。

取不到时自动退回提交对比（英文提交标题），再取不到就只说一句实话加一个 GitHub 入口。
所以**写不写都不影响用户能不能更新**，只影响他看到的内容是不是人话。

## 格式

另存一份为 `docs/release-notes/v<版本>.md`（文件名带 `v`，标题里的版本号不带 `v`，
与 `VERSION` 内容一致）。第一条标题写版本号，后面每一行是一条说明。只认这两种结构，
其余行（段落、引用、代码块）一律忽略：

```markdown
## 1.9.0

- 校园网：代理开着时不再误报「能上网」
- **重点**：寝室打卡支持每个账号独立时段
- 定位来源切换后立刻对自动打卡生效
```

- **版本号必须与 `VERSION` 一致**。写错版本会在 `release.yml` 里直接抛错、发布中止，
  不会把上一个版本的说明发给用户；客户端也会复核一次，不一致就退回提交对比。
- `- **重点**：…` 会显示成「重点 · …」，用来标出这次最值得看一眼的改动；普通条目不加前缀。
- 一行一条，尽量控制在 60 字以内 —— 界面是单行列表，太长会被截成一大段。
- 正文里的 `**`、`*`、反引号会被去掉（界面按纯文本渲染），不要指望 markdown 加粗生效。
- 最多 60 条，超出的部分不显示。
- 文件上限 32 KiB。

## 发布前检查

`release.yml` 会在 `gh release create` 之前检查文件存在、标题里有版本号、版本号与 tag 一致，
任一条不满足就中止发布。本地可以先跑：

```powershell
$version = (Get-Content VERSION -Raw).Trim()
Get-Content "docs\release-notes\v$version.md" -TotalCount 1
```

## 为什么不用 Release 正文

发布工作流用 `gh release create --generate-notes`，GitHub 对常规提交只生成一行 compare 链接
（实测 v1.8.5 的 Release 正文只有 80 字节），而且提交标题是英文。要让用户看到中文，
就得有人写 —— 写在文件里可以被发布流程校验，写在 Release 正文里不能。
